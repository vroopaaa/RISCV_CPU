Slide 2 • Core Frontend

Instruction Fetch & Branch Target Buffer (BTB)

How instructions enter the pipeline, how branches are speculated, and what hardware is assumed.

Frontend Flow & BTB Structure

fetch_n() Logic issueWidth n ≤ 10

1. Reads n consecutive words from Memory starting at fetch_pc.

2. For each slot, checks opcode:

  • Branch (0x63): BTB lookup • hash = (pc >> 2) & 0x7F
  • If BTB state ≥ 2 (WT / ST) → Predict Taken: redirect fetch_pc = target_pc
  • Else → Predict Not-Taken: continue fall-through fetch_pc += 4
  • Jump (0x6F, 0x67): No speculation → closes the fetch window!

⚠ Key Hardware Assumptions
  • • Multi-Word Single-Cycle Fetch: The core reads up to 10 instruction words (40 bytes) simultaneously from memory in a single cycle.
  • • Zero-Cycle I-Cache Hit: Fetch never stalls for cache line refills, alignment penalties, or DRAM latency.
  • • Mid-Window Redirection: If a branch predicts taken, subsequent slots in the same cycle's packet are fetched from the target address without bubble cycles!
  • • Mispredict Penalty: Handled by cancelling downstream instructions in the current window (windowCancelled[i]=true). No multi-cycle pipeline flush delay is modeled.
Multi-Core Consideration

In a 2 or 4-core system, multiple cores fetching 4-10 words per cycle will saturate any realistic memory bus immediately unless private L1 Instruction Caches (L1-I) are introduced.

Slide 3 • Execution Subsystem

Hazard Detection, ALUs & Single-Cycle Latency

Analysis of the hazard scanner, execution units, and arithmetic timing assumptions.

In-Order Hazard Scanner (hazard_scan) Prefix Picker

Scans slots 0 to fetchCount-1 and stops at the first structural or data hazard:

1. RAW (True Dependency):

If slot i reads an rs1 or rs2 that any prior slot j < i writes (rd), the issue window stops at i. No forwarding is modeled.

2. Memory Port Conflicts (MemClass):

Categorized into NONE, BANK_A, BANK_B, STORE.

  • Two stores conflict (single write port model).
  • Two loads into same NPU bank conflict (single bank write port).
  • Stores + NPU bank loads can co-issue (different physical ports).
3. WAR & WAW Hazards:

Implicitly hazard-free: all reads happen in execute_m() before any writes land in writeback_m(); sequential commit loop preserves latest rd value.

Functional Units & Timing Assumptions
Operation Type RSVP Latency Physical HW Reality
Integer ALU (add/sub/shifts) 1 cycle 1 cycle
RV32M MUL / MULH 1 cycle 2-4 cycles pipelined
RV32M DIV / REM 1 cycle 16-34 cycles (iterative divider)

Key Takeaway: Because every instruction executes in exactly 1 uniform cycle with in-order commit, the core requires zero register renaming, scoreboarding, or reorder buffers (ROB). If variable latency or non-blocking loads are introduced, a full pipeline scoreboarding mechanism is needed.
Slide 4 • Memory Subsystem

The Memory Subsystem: Current State vs. Reality

Investigating what caches exist today (spoiler: none), memory bandwidth, and latency models.

L1 Instruction Cache
NON-EXISTENT

PC accesses main memory vector directly via read_word(). Up to 10 reads per cycle with 0 wait-states.

L1 Data Cache
NON-EXISTENT

Loads and stores hit flat RAM directly. No cache lines, no dirty bits, no write-back or write-through buffers.

L2 / L3 Shared Cache
NON-EXISTENT

No intermediate caching layer. RAM is an unrestricted 4MB std::vector<uint8_t>.

The 4 Major Memory Assumptions in the Single-Core Model

1. Instantaneous Memory Access (0 Latency):

In real silicon, accessing off-chip DRAM takes 50–150 ns (~100 CPU cycles). In RSVP, memory access takes 0 nanoseconds — it is an in-memory C++ array lookup.

2. Infinite Memory Bandwidth:

In a single cycle, the CPU can fetch 10 instructions (40 bytes), perform multiple data loads/stores, and execute an NPU tile transfer (1,024 bytes) concurrently with no bus throttling.

3. Harvard Bus Decoupling:

Instruction fetch and data memory access never contend for a shared bus or port. Both paths independently invoke methods on the same Memory* instance.

4. Uniform Single Memory Address Space:

RAM occupies 0x00000000 to 0x003FFFFF (4MB), and NPU MMIO occupies 0x80000000+. All accesses are decoded synchronously inside Memory::read_word().

NPU Hardware Assumptions
  • • Instantaneous Compute: Writing to TRIGGER or MAC calculates 4,096 MACs in 0 simulation cycles. No busy-polling required.
  • • Instantaneous DMA: Tile transfers (load_a/load_b/store_c) move 1,024 bytes synchronously in a single cycle loop inside read_m().
  • • Tightly-Coupled Accelerator: The NPU is effectively an extension of the CPU's memory stage rather than an autonomous asynchronous DMA engine.
Multi-Core Challenge

If there is only 1 NPU in a 2 or 4-core SoC, which core owns it? Sharing the NPU requires hardware arbitration or mutex locking; otherwise, Core 1 will overwrite Matrix A while Core 0 is computing!

Key Architectural Decisions Needed:
  • NPU Topology: Does each core get a private NPU (4 NPUs total), or is 1 NPU shared via hardware queue?
  • Memory Bandwidth Bottleneck: 4 cores × 10 words fetch = 160 bytes/cyc. Needs banking or L1 caches.
  • Inter-Processor Interrupts (CLINT/MSIP): Core 0 dispatches jobs to Cores 1..3 via hardware doorbell interrupts.
Key Decisions to Agree On for Multi-Core:
1. NPU Allocation:

Option A: 1 shared NPU with MMIO mutex lock.
Option B: 1 private NPU per core (independent SRAMs).

2. Cache Hierarchy:

Option A: Uncached flat memory with round-robin arbiter (simplest functional step).
Option B: Add L1-I / L1-D caches with basic coherence.

3. Synchronization:

Implement standard RV32A instructions (LR/SC, AMO) vs. memory-mapped hardware mutex registers.
